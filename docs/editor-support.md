# Editor support and syntax highlighting

Editor support is installed separately from the Pfy runtime. The `.pfy`
extension identifies source files, while each editor needs a language
definition, grammar, or plugin to provide highlighting and editing features.

## VS Code

The [`vscode-pfy`](../vscode-pfy/) extension currently provides:

- `.pfy` file association and the **Pfy** language mode.
- TextMate syntax highlighting for headers, comments, keywords, strings,
  numbers, operators, and object keys.
- Bracket matching, indentation rules, snippets, and an optional file-icon
  theme.

To use the packaged extension, download the `.vsix` from the
[Pfy 1.0.0 release](https://github.com/Bxat01/Pfy-Language/releases/tag/v1.0.0)
and install it using **Extensions** → **…** → **Install from VSIX...**.

The extension is not yet published to the public Visual Studio Marketplace.
There is also no Pfy Language Server yet, so the extension does not provide
semantic completion, go-to-definition, or live parser diagnostics.

## What determines the colors?

The extension's TextMate grammar assigns scopes such as
`keyword.control.pfy`, `string.quoted.double.pfy`, and
`constant.numeric.decimal.pfy`. The user's selected VS Code theme maps those
scopes to actual colors. As a result, the same Pfy grammar works with light and
dark themes without hard-coding a color palette.

To inspect a token in VS Code:

1. Open a `.pfy` file.
2. Open the Command Palette and run **Developer: Inspect Editor Tokens and
   Scopes**.
3. Select a keyword, string, or operator to see its TextMate scope and the
   theme rule that colors it.

For custom colors, add scope rules to VS Code's `editor.tokenColorCustomizations`.
For example:

```json
{
  "editor.tokenColorCustomizations": {
    "textMateRules": [
      {
        "scope": "keyword.control.pfy",
        "settings": {
          "foreground": "#C586C0",
          "fontStyle": "bold"
        }
      },
      {
        "scope": "string.quoted.double.pfy",
        "settings": {
          "foreground": "#CE9178"
        }
      }
    ]
  }
}
```

These colors are examples, not required Pfy branding. Themes decide how scopes
look. See the official
[VS Code syntax highlighting guide](https://code.visualstudio.com/api/language-extensions/syntax-highlight-guide)
for tokenization, scopes, themes, and semantic highlighting.

## Supporting other editors

No repository setting can make every editor recognize a new language. Each
editor has its own language-extension system. A practical rollout is:

1. Publish the VS Code extension.
2. Reuse the TextMate grammar where an editor supports TextMate bundles.
3. Add native packages for Vim/Neovim, Sublime Text, JetBrains IDEs, Emacs,
   Zed, and other editors when there is a maintainer and a release path.
4. Consider a Tree-sitter grammar for editors and tools that support
   Tree-sitter.
5. Add an LSP server if users need completion, diagnostics, formatting, or
   navigation features across multiple editors.

TextMate highlighting only colors syntax. It does not parse a project or
provide semantic language features.

## Windows file association

Installing the VS Code extension makes VS Code identify `.pfy` files. It does
not install the `pfy` CLI or configure Windows to execute source files.
Install the CLI separately and add its directory to `PATH`. If desired, use
Windows **Open with** to associate `.pfy` files with VS Code. Avoid associating
them directly with the CLI unless you intentionally want double-clicking a
source file to execute it.

## File icons and logo

The VS Code extension includes an optional **Pfy Icons** file-icon theme.
Users select it with **Preferences: File Icon Theme → Pfy Icons**. The SVG
logo and PNG Marketplace icon live in `vscode-pfy/`.

Keep the same original Pfy mark and name across editor packages, documentation,
the repository social preview, and release pages. App icons and file icons are
visual branding; they do not register the language with an operating system.

## GitHub and GitLab language detection

GitHub's language bar is generated by
[Linguist](https://github.com/github-linguist/linguist). It currently detects
the C++ and CMake source in this repository; that is separate from VS Code
recognizing `.pfy` through its extension.

Linguist does not provide a normal per-repository switch that registers a new
language globally. To request official `.pfy` recognition, follow the current
[Linguist contribution guide](https://github.com/github-linguist/linguist/blob/main/CONTRIBUTING.md).
The usual contribution requires a language definition in `languages.yml`,
representative samples, and any required grammar and tests. Linguist reviews
new languages and extensions against its current usage and maintenance
criteria; acceptance is not automatic.

GitLab uses its own platform behavior and does not gain a custom language
definition just because a repository contains `.gitattributes` or a VS Code
extension. Check the current
[GitLab repository file documentation](https://docs.gitlab.com/user/project/repository/files/)
and the language-highlighting behavior of the GitLab instance you use. There
is no single setting that registers Pfy on every Git hosting service.
